# v0.1.1 — User Profile & Offboarding

สเปกสำหรับพัฒนาเวอร์ชัน 0.1.1 ต่อจาก 0.1.0 (commit `fa7f5a2`)

- ผู้ใช้ทุกคนดูและแก้ Profile ของตัวเองได้
- Admin ระงับผู้ใช้ที่ลาออกได้ทันทีหรือตั้งล่วงหน้า พร้อมโอนห้องประชุมและ Recording ให้ผู้รับช่วงต่อ
- ฟีเจอร์เสริม: บังคับเปลี่ยนรหัสผ่าน, จัดการอุปกรณ์ที่ล็อกอินอยู่, ค้นหา/กรอง/Export รายชื่อผู้ใช้, นำเข้าผู้ใช้จาก CSV

UI ของหน้าใหม่ทั้งหมดใช้ภาษาอังกฤษเหมือนหน้าเดิม ข้อความ UI ในเอกสารนี้จึงเขียนเป็นภาษาอังกฤษ

## 1. สิ่งที่มีอยู่แล้วใน 0.1.0

| เรื่อง | สถานะ | ที่อยู่ในโค้ด |
|---|---|---|

| MinIO | API identity (`api-reader`) อ่าน/ลบได้อย่างเดียว เขียนไม่ได้ | `infra/minio-init.sh` |

## 4. รายละเอียดฟีเจอร์

### F1 — My Profile + Avatar

**หน้า `/profile`** เปิดได้จากการคลิกชื่อ/รูปที่มุมล่างของ sidebar (`app-shell.tsx`) มี 3 ส่วน: **Profile**, **Password**, **Sessions**

ส่วน Profile:

| ฟิลด์ | ผู้ใช้แก้ได้ | Validation |
|---|---|---|
| Avatar | ได้ | ดูด้านล่าง |
| Display name | ได้ | 1–80 ตัวอักษร, trim |
| Phone | ได้ | ไม่บังคับ, สูงสุด 20 ตัว, อนุญาตเฉพาะ `+`, ตัวเลข, ช่องว่าง, `-` |
| First name / Last name | อ่านอย่างเดียว | — |
| Job title / Department | อ่านอย่างเดียว | — |
| Employee ID / Email / Role | อ่านอย่างเดียว | — |

ฟิลด์ที่อ่านอย่างเดียวแสดงข้อความ "Managed by your administrator"

**Avatar**

- รับ JPG, PNG, WebP ขนาดไม่เกิน 2 MB ตรวจชนิดไฟล์จาก magic bytes ไม่เชื่อนามสกุลหรือ `Content-Type`
- Server ตัดเป็นสี่เหลี่ยมจัตุรัส (cover) ย่อเป็น 256×256 แปลงเป็น WebP และลบ metadata ทั้งหมด (EXIF/GPS) แนะนำใช้ `sharp`
- เก็บใน MinIO bucket เดิมที่ key `avatars/<userId>/<random>.webp` เมื่ออัปโหลดใหม่ให้ลบไฟล์เก่า
- ดึงรูปผ่าน API เท่านั้น (ต้องล็อกอิน): `GET /api/users/:id/avatar?v=<avatarVersion>` ส่ง `Cache-Control: private, max-age=86400` โดย `avatarVersion` คือ timestamp ของ `avatarUpdatedAt` ใช้ทำ cache-busting
- ผู้ใช้ลบรูปตัวเองได้ Admin ลบรูปของคนอื่นได้ (กรณีรูปไม่เหมาะสม)
- ไม่มีรูปให้แสดงอักษรย่อเหมือนเดิม (`initials()`)

**จุดที่ต้องแสดง Avatar:** sidebar, `/profile`, Directory, ตาราง Users, หน้ารายละเอียดผู้ใช้ และ tile ในห้องประชุม (`components/meeting/tiles.tsx`) ใน LiveKit `identity` ของ participant คือ `userId` อยู่แล้ว ให้ใส่ `avatarVersion` ไว้ใน `metadata` ของ join token เพื่อให้ tile ประกอบ URL รูปได้

### F2 — เปลี่ยนรหัสผ่าน + บังคับเปลี่ยน

**เปลี่ยนเอง:** ส่วน Password ใน `/profile` ใช้ API `POST /auth/password` ที่มีอยู่แล้ว มีช่อง Current password, New password, Confirm new password

- รหัสใหม่อย่างน้อย 10 ตัว (`MIN_PASSWORD_LENGTH`) และต้องไม่ซ้ำรหัสปัจจุบัน
- สำเร็จแล้ว session อื่นถูก sign out (เป็นพฤติกรรมเดิมของ API) ให้แสดง toast บอกผู้ใช้

**บังคับเปลี่ยน:** เพิ่มคอลัมน์ `mustChangePassword`

- ตั้งเป็น `true` เมื่อ Admin สร้างผู้ใช้, Admin reset รหัส, นำเข้าจาก CSV และเปิดบัญชีคืน (F8)
- Admin แรกที่ seed จาก `.env` และผู้ใช้เดิมหลัง migrate มีค่าเป็น `false`
- ระหว่างที่ flag เป็น `true` ให้ `AuthGuard` อนุญาตแค่ `GET /auth/me`, `POST /auth/logout`, `POST /auth/password` ส่วน endpoint อื่นตอบ `403` พร้อม `code: "PASSWORD_CHANGE_REQUIRED"`
- `/auth/me` คืนค่า `mustChangePassword` ด้วย ฝั่ง web redirect ไปหน้า `/change-password` (หน้าเดี่ยว ไม่มี sidebar) จนกว่าจะเปลี่ยนสำเร็จ แล้วจึงกลับไปหน้า `next`
- เปลี่ยนสำเร็จแล้วตั้ง flag เป็น `false`

### F3 — Active sessions

**ข้อมูลที่เก็บเพิ่มใน `SessionData` (Redis):**

```ts
interface SessionData {
  userId: string;
  createdAt: string;
  publicId: string;    // random 16 bytes base64url ใช้อ้างอิงใน API/UI แทน hash ของ token
  ip: string;
  userAgent: string;   // raw สูงสุด 256 ตัวอักษร
  lastSeenAt: string;  // อัปเดตใน touch() แต่ไม่เกิน 1 ครั้งต่อ 60 วินาทีต่อ session
}
```

- แปลง User-Agent เป็น "Chrome on Windows" ฝั่ง server (เช่นใช้ `ua-parser-js`)
- Session ที่สร้างก่อน 0.1.1 ไม่มีข้อมูลเหล่านี้ ให้แสดงเป็น "Unknown device"
- ตอน list ถ้าเจอ id ใน `user-sess:<userId>` ที่ key `sess:` หมดอายุแล้ว ให้ `SREM` ทิ้ง

**ผู้ใช้ (ส่วน Sessions ใน `/profile`):** แสดงอุปกรณ์, IP, เวลาล็อกอิน, ใช้งานล่าสุด และป้าย "This device" บน session ปัจจุบัน
- ปุ่ม **Sign out** ต่อแถว (ยกเว้น session ปัจจุบัน ซึ่งใช้ปุ่ม Sign out ปกติ)
- ปุ่ม **Sign out all other devices**

**Admin (หน้ารายละเอียดผู้ใช้):** ดู session ของผู้ใช้คนนั้น และ sign out ทีละ session หรือทั้งหมดได้

### F4 — People directory

**หน้า `/people`** เพิ่มเมนู "People" ใน sidebar สำหรับทุก role

- ค้นหาจากชื่อที่แสดง, ชื่อ, นามสกุล, email
- กรองตามแผนก แบ่งหน้าละ 24 คน
- การ์ดแสดง Avatar, display name, ชื่อ-นามสกุล, ตำแหน่ง, แผนก, email
- แสดงเฉพาะบัญชีที่ active และไม่ถูก anonymize
- **ห้ามส่ง** เบอร์โทร, รหัสพนักงาน, role และสถานะการระงับใน response ของ Directory (กรองที่ API ไม่ใช่แค่ซ่อนใน UI)

### F5 — จัดการแผนก

**หน้า `/admin/departments`** เพิ่มเมนู "Departments" สำหรับ Admin

- เพิ่มแผนก และแก้ชื่อแผนก (1–100 ตัว, ห้ามซ้ำแบบไม่สนตัวพิมพ์เล็ก/ใหญ่)
- **Deactivate / Reactivate:** แผนกที่ deactivate จะไม่อยู่ใน dropdown แต่ผู้ใช้เดิมยังอ้างถึงได้ และแสดงเป็น "(inactive)"
- ไม่มีการลบแผนก เพื่อไม่ให้ข้อมูลผู้ใช้ค้าง
- แสดงจำนวนผู้ใช้ active ในแต่ละแผนก

### F6 — Admin แก้ Profile ผู้ใช้

**หน้า `/admin/users/[id]`** เปิดจากการคลิกแถวในตาราง Users

- **Profile:** แก้ได้ทุกฟิลด์ใน D2 ส่วน Avatar ทำได้แค่ลบ
- **Account:** role, reset password (ย้าย modal เดิมมาไว้ที่นี่ด้วย), last login, created at
- **Status:** สถานะปัจจุบัน และปุ่ม Suspend, Cancel scheduled suspension, Reactivate, Anonymize ตามสถานะ
- **Sessions:** ตาม F3
- **Suspension history:** ประวัติการระงับ/ยกเลิก/เปิดคืนทั้งหมด

กฎ:
- **Employee ID:** 1–32 ตัว, อนุญาต `A-Z a-z 0-9 - _`, เก็บเป็นตัวพิมพ์ใหญ่, unique
- **ฟิลด์บังคับ:** บังคับตอนสร้างผู้ใช้ใหม่เท่านั้น ถ้าบัญชีเดิมยังไม่มีค่า ไม่ต้องบังคับให้เติมตอนแก้ไขฟิลด์อื่น
- **เปลี่ยน email:** ต้องไม่ซ้ำ เก็บเป็นตัวพิมพ์เล็ก บันทึก audit โดยเก็บ email เก่าและใหม่
- **ข้อห้ามที่มีอยู่แล้ว:** ยังคงห้ามลด role ของตัวเอง
- **Create user modal:** เพิ่มช่อง Employee ID (บังคับ), first/last name, job title, department, phone (ไม่บังคับ)

### F7 — ระงับผู้ใช้ (Offboarding)

**Suspend modal** (เปิดจากหน้ารายละเอียดผู้ใช้ หรือเมนูในแถวของตาราง Users)

| ฟิลด์ | รายละเอียด |
|---|---|
| Reason (บังคับ) | `RESIGNED` Resigned · `TERMINATED` Terminated · `LONG_LEAVE` Long leave · `SECURITY` Security concern · `OTHER` Other |
| Note | สูงสุด 500 ตัว บังคับเมื่อเลือก `OTHER` |
| Effective | **Now** หรือ **Last working day** (เลือกวันที่ ระงับมีผลเวลา 23:59 Asia/Bangkok ของวันนั้น ต้องเป็นวันนี้หรือในอนาคต) |
| Hand over to | ค้นหาผู้ใช้ที่ active (ไม่รวมคนที่กำลังถูกระงับ) ถ้าไม่เลือก จะโอนให้ Admin ที่สั่งระงับ |

ใน modal แสดงสรุปก่อนยืนยัน (จาก `GET /admin/users/:id/offboarding-summary`) เช่น
> "2 active meetings and 5 meetings with recordings will be handed over to Somchai K. All sessions will be signed out."

**กฎ**

- ห้ามระงับตัวเอง
- ห้ามระงับ Admin ที่ active คนสุดท้าย
- ผู้ใช้หนึ่งคนมีการระงับสถานะ `SCHEDULED` หรือ `ACTIVE` ได้แค่ 1 รายการ (partial unique index)
- ถ้าจะเปลี่ยนวันหรือผู้รับช่วงของรายการ `SCHEDULED` ให้ Cancel แล้วตั้งใหม่

**สิ่งที่เกิดขึ้นเมื่อการระงับมีผล** (ทั้งแบบ Now และตอน job ทำงาน) ทำใน transaction เดียวกันเท่าที่ทำได้:

1. `users.is_active = false`
2. โอน host: ทุก meeting ที่ `host_id = <user>` ทั้ง `ACTIVE` และ `ENDED` เปลี่ยน `host_id` เป็นผู้รับช่วง สิทธิ์จัดการ Recording ผูกกับ host ของ meeting อยู่แล้ว (`canManageMeeting`) Recording จึงย้ายตามไปด้วย ส่วน `recordings.requested_by` และ `meetings.created_by` ไม่แก้ เพราะเป็นประวัติ
3. การระงับเปลี่ยนเป็นสถานะ `ACTIVE` และบันทึก `applied_at`
4. หลัง commit: `sessions.destroyAllForUser()` และเตะออกจากห้อง LiveKit (`evictFromActiveMeetings` เดิม) ห้องไม่ปิด และ Recording ที่กำลังอัดอยู่อัดต่อ
5. บันทึก audit `user.suspended` และ `meeting.host_transferred` (1 รายการต่อ meeting พร้อม `from` และ `to`)

**ผู้รับช่วง ณ เวลาที่มีผล:** ตรวจอีกครั้งตอนมีผล ถ้าผู้รับช่วงไม่ active แล้ว ให้โอนให้ Admin ที่สั่งระงับ ถ้า Admin คนนั้นก็ไม่ active ให้โอนให้ Admin ที่ active ซึ่งสร้างบัญชีเก่าที่สุด และบันทึกเหตุผลลง audit

**Scheduled job**

- `@Interval(60_000)` ใน `SuspensionService` หารายการ `SCHEDULED` ที่ `effective_at <= now()`
- claim ด้วย `UPDATE ... WHERE status = 'SCHEDULED'` ก่อนประมวลผล เพื่อให้ idempotent
- ถ้าประมวลผลรายการไหน error ให้ log แล้วข้ามไปทำรายการถัดไป แล้วลองใหม่ในรอบหน้า
- ก่อนถึงเวลา ผู้ใช้ใช้งานได้ตามปกติ และตาราง Users แสดงป้าย "Leaving on 31 Oct 2026"

**ข้อความตอนล็อกอิน (D10):** ใน `POST /auth/login` ถ้า user มีอยู่และรหัสผ่านถูก แต่ `isActive = false`:
- ตอบ `403` พร้อม `{ code: "ACCOUNT_SUSPENDED", message: "This account has been suspended. Please contact your administrator." }`
- **ไม่นับ**เป็น failure ของ rate limit เพราะรหัสผ่านถูก
- บันทึก audit `auth.login_failed` ด้วย `reason: "suspended"`

กรณีอื่นใช้ข้อความ `Invalid email or password` เหมือนเดิม และหน้า login ต้องแสดงข้อความตาม `code`

### F8 — เปิดบัญชีคืน + Anonymize

**Reactivate:** ทำได้เฉพาะบัญชีที่ระงับแล้วและยังไม่ถูก anonymize

- ใน modal ให้ Admin ตั้งรหัสผ่านใหม่ (บังคับ) และใส่หมายเหตุได้
- ผลลัพธ์: `isActive = true`, `mustChangePassword = true` และการระงับเปลี่ยนเป็น `LIFTED`
- ห้อง/Recording ที่โอนไปแล้ว **ไม่โอนกลับอัตโนมัติ**

**Anonymize:** ทำได้เฉพาะบัญชีที่ถูกระงับและมีผลแล้ว (`ACTIVE`) ย้อนกลับไม่ได้ Admin ต้องพิมพ์ email ของผู้ใช้เพื่อยืนยัน

| ข้อมูล | ผลลัพธ์ |
|---|---|
| `email` | `anonymized-<userId>@anonymized.invalid` |
| `displayName` | `Former user #XXXX` (`XXXX` = 4 ตัวแรกของ userId ตัวพิมพ์ใหญ่) |
| first/last name, phone, employee ID, job title, department | `null` |
| Avatar | ลบ object ใน MinIO และตั้ง `avatarKey = null` |
| `passwordHash` | hash ของค่าสุ่มที่ไม่มีใครรู้ |
| `note` ของการระงับทุกรายการ | `null` (เก็บแค่หมวดเหตุผล) |
| `anonymizedAt` | เวลาปัจจุบัน |
| Meeting / Recording / Audit log | คงเดิม (ชื่อในประวัติจะกลายเป็น "Former user #XXXX") |

> **หมายเหตุ PDPA:** `metadata` ของ audit log เก่ายังมี email ของผู้ใช้อยู่ (เช่นใน `auth.login_failed`) ตามที่ตกลงให้ audit log คงเดิม การกำหนดระยะเวลาเก็บ audit log อยู่ใน Backlog

### F9 — ค้นหา/กรองผู้ใช้ + Last login + Export CSV

**ตาราง `/admin/users`**

| ส่วน | รายละเอียด |
|---|---|
| คอลัมน์ | User (avatar, display name, email) · Employee ID · Department · Role · Status · Last login |
| ค้นหา | ชื่อ, email, employee ID |
| ตัวกรอง | Role, Department, Status (`Active` / `Leaving` / `Suspended` / `Anonymized`) |
| เรียงลำดับ | ชื่อ, last login, created at |
| แบ่งหน้า | หน้าละ 25 แถว |
| สถานะใน URL | เก็บค่าตัวกรองไว้ใน query string เพื่อให้ refresh หรือแชร์ลิงก์ได้ |

**Last login:** เพิ่มคอลัมน์ `last_login_at` อัปเดตเมื่อ login สำเร็จ

**Export CSV:** ปุ่ม Export เรียก `GET /admin/users/export.csv` โดยใช้ตัวกรองเดียวกับตาราง (ทุกหน้า ไม่ใช่แค่หน้าปัจจุบัน)

- **Encoding:** UTF-8 พร้อม BOM เพื่อให้ Excel แสดงภาษาไทยถูก
- **คอลัมน์:** `employee_id, email, display_name, first_name, last_name, job_title, department, phone, role, status, suspension_reason, effective_at, last_login_at, created_at`
- **ป้องกัน CSV injection:** ถ้าค่าในเซลล์ขึ้นต้นด้วย `= + - @` tab หรือ CR ให้เติม `'` นำหน้า
- **Audit:** บันทึก `users.exported` พร้อมตัวกรองและจำนวนแถว

### F10 — นำเข้าผู้ใช้จาก CSV

**Flow:** Admin → Users → **Import** → ดาวน์โหลด template → อัปโหลด → Preview → Import → ดาวน์โหลดไฟล์รหัสผ่านชั่วคราว

**รูปแบบไฟล์**

- UTF-8 (รองรับ BOM จาก Excel), ไม่เกิน 1 MB, ไม่เกิน 500 แถว (ไม่นับ header)
- Header (เรียงตามนี้): `email, display_name, role, employee_id, first_name, last_name, job_title, department, phone`
- ไม่มีคอลัมน์รหัสผ่าน

**Validation (ทุกแถว)**

| คอลัมน์ | กฎ |
|---|---|
| `email`, `display_name`, `role`, `employee_id` | บังคับ ใช้กฎเดียวกับ F6 |
| `role` | `ADMIN`, `HOST`, `MEMBER` (ไม่สนตัวพิมพ์เล็ก/ใหญ่) |
| `department` | ต้องตรงกับชื่อแผนกที่ active (ไม่สนตัวพิมพ์เล็ก/ใหญ่) ไม่สร้างแผนกใหม่ให้อัตโนมัติ |
| ความซ้ำ | `email` และ `employee_id` ต้องไม่ซ้ำกันเองในไฟล์ และไม่ซ้ำกับฐานข้อมูล |

**Preview:** `POST /admin/users/import/preview` (multipart)

- parse และ validate ทั้งไฟล์ แล้วเก็บข้อมูลที่ parse แล้วไว้ใน Redis 15 นาที คืน `importId` พร้อมรายการแถวและ error ของแต่ละแถว (เลขแถว, คอลัมน์, ข้อความ)
- UI แสดงตาราง preview ไฮไลต์แถวที่ผิด ถ้ามี error แม้แต่แถวเดียว ปุ่ม Import จะกดไม่ได้

**Commit:** `POST /admin/users/import/commit { importId }`

- นำเข้าแบบ **all-or-nothing** ใน transaction เดียว และ validate ซ้ำอีกรอบก่อนเขียน
- สร้างรหัสผ่านสุ่ม 14 ตัวจากชุดตัวอักษรที่ไม่ชวนสับสน (ไม่มี `0 O 1 l I`) ตั้ง `mustChangePassword = true`
- Response คือไฟล์ CSV `email, display_name, employee_id, temporary_password` ให้ดาวน์โหลด**ครั้งเดียว** server ไม่เก็บรหัสผ่าน plain text ไว้ที่ไหน และลบ `importId` ออกจาก Redis ทันที
- UI เตือนก่อนกด: "Temporary passwords are shown only once. Store the file securely and delete it after distributing."

**Audit:** บันทึก `user.created` ต่อคน (`metadata.source = "csv_import"`) และ `users.imported` 1 รายการพร้อมจำนวนคน ห้ามมีรหัสผ่านใน audit

- Suspension state machine: `SCHEDULED → ACTIVE → LIFTED`, `SCHEDULED → CANCELLED`, ห้ามมีรายการเปิด 2 รายการ, ห้ามระงับตัวเอง, ห้ามระงับ Admin คนสุดท้าย, การ fallback ผู้รับช่วง
- คำนวณ `effectiveAt` = 23:59 Asia/Bangkok ของวันที่เลือก (ทดสอบข้ามเที่ยงคืน UTC)
- CSV: BOM, header ผิด, แถวซ้ำในไฟล์/ใน DB, เกิน 500 แถว, แผนกไม่มีอยู่, CSV injection ตอน export
- Anonymize: ทุกฟิลด์ตามตาราง F8 ถูกล้าง

### E2E (Playwright, `tests/e2e`)

1. Admin สร้าง user → user ล็อกอิน → ถูกบังคับไป `/change-password` → เปลี่ยนแล้วเข้า Home ได้
2. User แก้ display name + อัปโหลด avatar → เห็นใน sidebar และใน Directory ของ user อื่น
3. User อีกคนเปิด Directory → response ไม่มี `phone` และ `employeeId`
4. User เป็น host ห้อง ACTIVE → Admin สั่ง Suspend now พร้อมเลือกผู้รับช่วง → user ถูกเตะออกจากห้อง, session หมด, ล็อกอินแล้วเห็น "suspended" → ผู้รับช่วงควบคุมห้องและเห็น Recording ได้
5. ตั้งระงับล่วงหน้า (ทดสอบด้วยการแก้ `effective_at` ใน DB ให้เป็นอดีต) → ภายใน 60 วินาทีบัญชีถูกระงับ
6. Reactivate → ล็อกอินได้และถูกบังคับเปลี่ยนรหัส
7. Import CSV 3 แถว (1 แถวผิด) → Import กดไม่ได้ → แก้ไฟล์ → นำเข้าได้ → ล็อกอินด้วยรหัสชั่วคราวได้
8. Sessions: ล็อกอิน 2 browser context → sign out อีกเครื่องจาก `/profile` → เครื่องนั้นถูกพาไป `/login`

### เกณฑ์รับงาน

- [ ] Avatar ที่อัปโหลดไม่มี EXIF และขนาด 256×256 WebP
